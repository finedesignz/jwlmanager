  <name>Task 1: Resolve D7-03 — does recolor union-merge?</name>
  <decision>Whether highlight recolor invokes the geometric BlockRange union-merge, or whether the merge primitive ships standalone (strict Python parity).</decision>
  <context>
ROADMAP Phase 7 criterion 1 says overlapping ranges are union-merged "exactly as the Python app does". Verified against source: the Python `set_color` (`JWLManager.py:3237-3278`) does NOT merge — it only `UPDATE`s `ColorIndex`. The geometric union-merge lives exclusively in `add_usermark` (`:2160-2184`), the IMPORT path. Wiring merge-on-recolor would be a behavior the Python app never had, applied to a code path that DELETEs BlockRange rows on a geometric predicate — an off-by-one on token boundaries silently destroys highlight geometry with no user-visible signal.

Reversibility: **one-way**. Once a user recolors and saves, absorbed BlockRange rows are gone; no undo exists.

Planner's recorded resolution (carried forward from the discuss session, and the option this plan is written against): **Option A** — port `merge_block_ranges` as a standalone, exhaustively tested primitive (needed anyway for Phase 8 import) and do NOT wire merge-on-recolor. Criterion 1 is then satisfied by the primitive existing and being round-trip tested, not by recolor merging. The UI-SPEC's Color dialog copy already assumes this and contains no merge clause.
  </context>
  <options>
    <option id="option-a">
      <name>Strict Python parity — primitive standalone, recolor does not merge (RECOMMENDED, plan written against this)</name>
      <pros>Faithful to the behavioral oracle; the dangerous geometry ships fully tested but with no user-facing trigger until Phase 8; no silent, irreversible geometry loss; UI copy already matches</pros>
      <cons>ROADMAP criterion 1 is satisfied indirectly (primitive tested, not recolor-invoked) and that reading must be recorded explicitly in the SUMMARY</cons>
    </option>
    <option id="option-b">
      <name>Extend beyond parity — recolor invokes merge_block_ranges</name>
      <pros>Literal reading of ROADMAP criterion 1</pros>
      <cons>Introduces irreversible, silent geometry destruction on a path the Python never merged on; requires an added Color-dialog summary clause ("{K} overlapping highlights will be combined into one"); diverges from the archive behavior users' existing Python-app workflow produces</cons>
    </option>
  </options>
  <reversibility rating="one-way">Absorbed BlockRange rows are deleted; after save there is no recovery path.</reversibility>
  <resume-signal>Select: option-a or option-b</resume-signal>
