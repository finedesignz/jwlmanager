<objective>
Ship tag add/remove/rename (EDIT-03) and archive-wide tag reorder (EDIT-04), and introduce the Utilities menu — the app's first selection-independent operation surface.

Purpose: EDIT-04 is the phase's load-bearing correctness item. `TagMap` carries `UNIQUE(TagId, Position)`, so a single-pass renumber collides mid-loop. EDIT-03 carries the tri-state and ID-recycling behaviors that make output comparable with the Python app's.
Output: `db/tags.rs`, `db/reorder.rs`, two command pairs, `TagDialog.tsx`, `UtilitiesMenu.tsx`, and a new "Utilities ▾" CommandBar button.

**D7-05 resolved — reuse the shipped `redensify_tag_positions` staging technique, not the Python two-pass.** Rationale recorded here and to be restated in the SUMMARY: `app/src-tauri/src/db/trim.rs:171-205` already solves the identical `UNIQUE(TagId, Position)` collision on the identical table via TEMP-table staging; it is shipped, tested, and exercised on every save. Reusing it is the smaller diff and the Karpathy-aligned choice, and it keeps reorder and save's re-densify on one technique so their composition is trivially idempotent. The Python's negative-position two-pass is an equivalent collision-free rewrite, not a distinct observable behavior — the observable contract is identical (0-based dense positions per tag, ordered by NoteId), and the round-trip test asserts that contract, not the intermediate negatives. If the executor finds ANY observable behavioral difference between the two techniques, stop and report it rather than proceeding.
</objective>
