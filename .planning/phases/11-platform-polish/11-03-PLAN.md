**Why this is a separate plan from the rest of the i18n work.** A grep sample
across `app/src/components/*.tsx` found 48 `aria-label`/`title`/`placeholder`
attribute matches and 14 JSX-text-node matches in a single narrow-regex pass
alone (RESEARCH's own Pitfall 3 explicitly calls this an undercount) spread
across 13 component files -- `CommandBar.tsx` alone carries roughly two dozen
button labels, dialog titles, and pluralized/interpolated summary sentences.
Retrofitting all of that plus building the i18n architecture from scratch in
one plan would blow past this project's ~50% single-plan context budget
(planner_authority_limits: context cost is a legitimate split reason).
`11-01-PLAN.md`'s own scope_boundary already anticipated this split, referring
to "plans 11-03/11-04" for the i18n layer. This plan builds the architecture
and proves it completely on two components; **plan 11-04 retrofits the
remaining 13 components and lib/errors.ts** using the exact API this plan
ships.

**In this plan:** the catalog/context architecture, all 9 locale files (1
complete + 8 scaffolded), the functional language switcher UI, and full
retrofit of App.tsx + SettingsDialog.tsx.

**Explicitly NOT in this plan, and NOT omitted from PLAT-03 -- deferred to
11-04 for context-budget reasons:** CommandBar, CategorySwitcher,
CategoryList, TagDialog, FavoriteAddDialog, MediaAddDialog,
EditPreviewDialog, FoldMergeDialog, RecordEditor, ColorMenu, UtilitiesMenu,
ErrorBanner, JwlCoreNotice, and `lib/errors.ts`'s `describeError` copy. A
component list this concrete is deliberate -- 11-04's planner does not need
to re-derive it.

**Locale coverage is English-complete + extensible structure only (D11-02).**
Real translations for the other 8 languages are a follow-up milestone item
needing a translation resource this environment does not have. Do not
fabricate content for them here or in 11-04.

**No Rust changes.** `AppSettings.language` and its persistence already exist
end to end from 11-01. This plan and 11-04 are both frontend-only.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| settings file -> language value | `language` is a free-form `String` (not a closed enum) read back from disk by 11-01's `load_settings`; this plan's `I18nProvider` is the first consumer that looks it up as a locale key |
| frontend -> `t()` params | `t(key, params)` accepts caller-supplied values (e.g. a version string) for template substitution |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-12 | Denial of service | an unrecognized or hand-edited `language` value used as a locale key | low | mitigate | `catalogs[locale]` on an unknown key is simply `undefined`, and the `?? en[key]` fallback resolves every key to English -- proven by `I18nContext unknown locale` (task 2). No throw, no blank render |
| T-11-13 | Tampering | a `language` value used to build a filesystem path, query, or command | low | accept | `language` is only ever an in-memory lookup key into a TypeScript record; it is never interpolated into a path, query, or shell command anywhere in this plan (already noted in 11-01's own threat register as T-11-03, reaffirmed here as this plan is the actual consumer) |
| T-11-14 | Denial of service | a caller-supplied `params` object designed to loop or throw during token substitution | low | mitigate | The substitution is a single bounded regex `.replace` pass over the resolved template string; an unmatched `{token}` is left literal rather than raising, and no recursive or user-controlled template lookup exists |
| T-11-SC | Tampering | npm dependency supply chain | low | accept | Zero new dependencies -- the catalog is a plain TypeScript `Record`, the context is plain React `createContext`/`useContext`. RESEARCH's Package Legitimacy Audit is N/A |
</threat_model>
