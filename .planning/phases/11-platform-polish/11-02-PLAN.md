<objective>
Wire Windows Authenticode signing through Azure Trusted Signing into the Tauri
bundling step, adapted from the working sibling implementation in remo-code, and
make the wiring reviewable and fail-closed in an environment where no signing
credentials exist and none can be created.

Purpose: PLAT-02's criterion is about WHERE signing happens -- inside bundling,
via the bundler's own hook -- because a post-bundle pass silently breaks updater
verification. Getting the ordering right now costs nothing; re-discovering it
after an auto-update milestone ships costs a broken update channel.

Output: a committed-but-inert signing script and metadata, a new tag-triggered
release workflow that stays green unsigned today and becomes a signing build the
moment three secrets and one variable are provisioned, a guard test against
accidentally committing a live sign command, and a documented manual signature
verification procedure.
</objective>

<design_resolutions>
Settled during planning; do not re-derive or re-litigate.

**New workflow file, new tag prefix -- DECIDED.** Add a NEW tag-triggered
`.github/workflows/release-app.yml` gated on an `app-v*` tag prefix. Do NOT
extend `app-ci.yml`, which carries an explicit "No code signing here" comment
and is the PR/push matrix. Do NOT reuse the bare `v*` prefix -- it belongs to
the existing Python app's `release.yml` in this same repository and would
collide.

**Signing the vendored jwlCore library is OUT OF SCOPE -- DECIDED.** It is a
prebuilt binary this repository does not build. Record it as a documented
residual risk in `docs/signing.md`, not as a task. SmartScreen reputation
applies to the top-level installer a user runs; a resource library loaded at
runtime is not independently gated the same way. If friction is ever observed
specifically on that library, that is a re-scope, not a Phase 11 blocker.

**Certificate profile is REUSED, not provisioned.** One Trusted Signing account
and one certificate profile sign many products -- that is how the service is
designed. Copy the account, profile, and endpoint values from the sibling
implementation's metadata file verbatim. Do not create a jwlmanager-specific
profile.

**Acceptance is about WIRING, not about a signed artifact.** The three Azure
secrets and the enable variable are absent from this repository and cannot be
provisioned from this environment (verified: both the secret list and the
variable list are empty). No task here may have "the installer is signed" as its
acceptance criterion -- that is unsatisfiable. What IS verifiable: the committed
config has no sign-command entry, the unsigned path is green, the script exits
non-zero when the dlib variable is unset, and the injected string agrees with the
script's on-disk location. Actual signature verification is a MANUAL
post-credential step recorded in 11-VALIDATION.md.

**Path depth differs from the reference -- the one thing NOT to copy verbatim.**
The sibling's script sits one level above its Tauri project root, so its injected
command points one directory up. Here `app/src-tauri` IS the Tauri project root
and the script sits inside it, so the injected command must point at the script
WITHIN that directory, not above it. Getting this wrong yields a build that
either fails loudly (acceptable) or silently resolves a different path
(dangerous). Task 3 exists to prove the fail-closed direction.

**NuGet invocation is copied verbatim, including an absence.** The reference
records a real incident where adding a version-exclusion flag broke the install
step and a build reported success having skipped signing. The flag's absence is
intentional -- the default layout keeps the version in the folder name, which is
what the dlib path construction expects. Copy the invocation and its explanatory
comment together.

**Version pin.** Reuse the proven-working Trusted Signing client version pin
from the reference (1.0.60). Bumping it is an operational decision for whoever
provisions credentials, not a planning decision here.
</design_resolutions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub secret store -> CI job environment | the three Azure credentials cross into a runner process; any log statement touching them publishes them |
| public NuGet feed -> CI runner | the Trusted Signing client is fetched fresh each run into the build environment |
| CI workspace -> released artifact | the injection step mutates the Tauri config in the workspace; whatever it writes decides whether the shipped installer is signed |
| repository -> end user | the installer a user downloads and runs is the artifact SmartScreen judges |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-06 | Information disclosure | Azure credentials in CI logs | high | mitigate | Credentials appear only in an env mapping on the build step; the script prints paths only. The prohibition against adding a debug print of a credential while troubleshooting is explicit in must_haves.prohibitions and reviewed in task 2's acceptance |
| T-11-07 | Spoofing | an unsigned artifact shipped while the build reports success | high | mitigate | The script refuses to run without the dlib variable and exits non-zero, so once the hook is injected an unconfigured build FAILS rather than passing silently; the deliberate-fail-closed procedure in docs/signing.md proves the hook is actually invoked before any green build is trusted |
| T-11-08 | Tampering | a live sign-command entry accidentally committed, breaking or misdirecting every future build | medium | mitigate | The guard test in signing_wiring.rs fails CI on any committed hook, and is itself proven to guard by a red/green demonstration |
| T-11-09 | Tampering | supply chain of the NuGet-fetched signing client | medium | accept | Microsoft's own official package on the public feed, pinned to the version already running in production in the sibling repository; same trust boundary the GitHub-hosted runner already operates in. CI-only tooling, never enters Cargo.lock or package-lock.json |
| T-11-10 | Repudiation | signature validity lost when the short-lived certificate expires | low | mitigate | The RFC-3161 timestamp countersignature is part of the signtool invocation; validity survives certificate expiry by design. No renewal logic is added -- adding any would be a defect |
| T-11-11 | Spoofing | the vendored jwlCore library ships unsigned inside a signed installer | medium | accept | Out of scope by decision -- it is a prebuilt binary this repository does not build. SmartScreen judges the top-level installer. Recorded as a named residual risk in docs/signing.md so a later observation of friction is a re-scope with a paper trail, not a surprise |
| T-11-SC | Tampering | Cargo / npm dependency supply chain | low | accept | Zero new project dependencies; the signing toolchain is entirely CI-side |
</threat_model>
