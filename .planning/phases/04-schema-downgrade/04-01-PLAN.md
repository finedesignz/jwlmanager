<schema_facts>
<!-- VERIFIED against res/blank (userData.db, user_version=16) during planning. -->
FOUR remap targets carry a composite UNIQUE/PK in which the remapped column participates. Merging two Locations that share the secondary key makes a blind `UPDATE ... SET <col>=survivor` VIOLATE the constraint. PK/UNIQUE enforcement is INDEPENDENT of `PRAGMA foreign_keys=OFF` — the FK-off guard does NOT protect these. All four need dedup-then-repoint (Task 2 step c):

| Remap target | Constraint at risk | Secondary key for dedup |
|---|---|---|
| TagMap.LocationId | `UNIQUE (TagId, LocationId)` | TagId |
| Bookmark.PublicationLocationId | `CONSTRAINT PublicationLocationId_Slot UNIQUE (PublicationLocationId, Slot)` | Slot |
| InputField.LocationId | `PRIMARY KEY (LocationId, TextTag) WITHOUT ROWID` | TextTag |
| PlaylistItemLocationMap.LocationId | `PRIMARY KEY (PlaylistItemId, LocationId) WITHOUT ROWID` | PlaylistItemId |

SAFE (plain repoint, no LocationId-participating uniqueness): `Bookmark.LocationId` (the FIRST bookmark column — only PublicationLocationId has the Slot UNIQUE), `Note.LocationId`, `UserMark.LocationId`.

**The two Location UNIQUEs cover ALL rows, but the merge only touches null-Book/Chapter rows.** U2 was ABSENT in v16, so a v16 archive may hold rows that will violate U1 or U2 once the v14 Location table is rebuilt — INCLUDING rows the merge never touches (e.g. two scripture rows with non-null BookNumber sharing the six U2 columns but differing only by Specialty/Edition, which was legal in v16). These are legitimately un-downgradeable archives; the transform MUST detect this and fail cleanly with rollback (HIGH-1), never a partial write.

- TagMap/Bookmark/InputField/PlaylistItemLocationMap DDL is identical in v14/v16 (only Location changes). No rebuild of these tables.
- 6 dependent tables / 7 FK columns is the COMPLETE LocationId FK set in v16 (research audit). No hidden FK.

  <name>Task 2: Implement downgrade_to_v14 — typed-key remap closure + preflight + DDL rebuild</name>
  <files>app/src-tauri/src/archive/downgrade.rs</files>
  <behavior>
    - Version gate: `user_version==14` → no-op `Ok(())`; `!=16` (and !=14) → `Err(SchemaDowngradeFailed)`; `==16` → run.
    - After a successful run on a fixture with a 3-way collision (ids 50/20/90 sharing the v14 key, BookNumber/ChapterNumber NULL): survivor is `20` (lowest); Locations 50 and 90 are gone; user_version=14.
    - Two merged Locations sharing a Bookmark Slot / an InputField TextTag / a PlaylistItem: no error, survivor's row kept, merged-away colliding row gone, no dangling reference, no UNIQUE/PK violation.
    - A Location with literal `KeySymbol='None'` is NOT merged with a NULL-KeySymbol Location (typed key, MED-4).
    - Two EXCLUDED Locations (non-null BookNumber) colliding on U2 that the merge cannot fix → `Err(SchemaDowngradeFailed)`, DB still user_version=16, original rows intact (HIGH-1).
    - Rollback: an injected failure leaves user_version=16 and the original Location row-set intact, returning SchemaDowngradeFailed.
  </behavior>
  <action>
Implement `pub fn downgrade_to_v14(conn: &mut Connection) -> Result<(), ArchiveError>` mirroring `upgrade_to_v16`'s structure (upgrade.rs:205-242):

1. Read `PRAGMA user_version`. `==14` → `Ok(())` (idempotent). If not 16 → `Err(SchemaDowngradeFailed { reason: "expected user_version 16, found {v}" })`.
2. `conn.execute_batch("PRAGMA foreign_keys = OFF;")` BEFORE opening the tx (pragma no-op inside an active tx — upgrade.rs:229 finding 6; this build does NOT default FK off). Wrap in a `PragmaGuard` (restores on return; guard borrows `&conn`; use `conn.unchecked_transaction()` like delete.rs:224). Set FK off AFTER constructing the guard.
3. Open transaction. Call `run_downgrade_ddl(&tx)`. On Ok, `tx.commit()`; any Err rolls back on drop. Map every rusqlite error through `map_sqlite_err`.

Implement `fn run_downgrade_ddl(tx: &Transaction) -> Result<(), ArchiveError>`:

a. **Grouping (MED-4 — typed tuple key, NOT a stringified key):** run the grouping query WITH `ORDER BY LocationId`. Collect into `BTreeMap<GroupKey, Vec<i64>>` (or `HashMap` + a separate ordered Vec of first-seen keys) where `GroupKey = (Option<String>, Option<i64>, Option<i64>, Option<i64>, Option<i64>, i64)` = `(KeySymbol, IssueTagNumber, MepsLanguage, DocumentId, Track, Type)` read via `row.get::<_, Option<_>>(..)`. A REAL `KeySymbol='None'` must NOT collide with SQL NULL — that is exactly why the key is a typed `Option` tuple, not Python's f-string `"None"` join (:1176). Document this as a deliberate correctness divergence from Python's stringify bug, same spirit as D4-01. Because rows arrive ascending by LocationId, `ids[0]` per group is the LOWEST — the survivor. Preserve first-seen group order + intra-group insertion order.

b. **Remap:** for each group with `len>1`, `keep_id = ids[0]`; for each `old_id` in `ids[1..]`, apply the per-column handling below (verbatim column order per JWLManager.py:1185-1191), all parameterized binding `(keep_id, old_id)`, then `DELETE FROM Location WHERE LocationId = ?old_id`.

c. **Per-column handling — dedup-then-repoint for the FOUR composite-key targets, plain repoint for the other three.** PK/UNIQUE enforcement is INDEPENDENT of FK-off, so a blind `UPDATE` RAISES when the two merged Locations share the secondary key. For each of the four, FIRST DELETE the merged-away Location's rows that collide with the survivor on the composite key (these are real deleted study rows — Wave 2's dry-run reports them as data loss, HIGH-3), THEN plain-`UPDATE` the rest. NEVER bare `UPDATE OR IGNORE` — the skipped row would remain pointing at the DELETEd `old_id` (dangling reference). In column order:
   1. `Bookmark.LocationId` — **plain repoint**: `UPDATE Bookmark SET LocationId=?keep WHERE LocationId=?old`.
   2. `Bookmark.PublicationLocationId` — **dedup** on `UNIQUE (PublicationLocationId, Slot)`: `DELETE FROM Bookmark WHERE PublicationLocationId=?old AND Slot IN (SELECT Slot FROM Bookmark WHERE PublicationLocationId=?keep)`; then `UPDATE Bookmark SET PublicationLocationId=?keep WHERE PublicationLocationId=?old`.
   3. `Note.LocationId` — **plain repoint**.
   4. `UserMark.LocationId` — **plain repoint**.
   5. `InputField.LocationId` — **dedup** on `PRIMARY KEY (LocationId, TextTag)`: `DELETE FROM InputField WHERE LocationId=?old AND TextTag IN (SELECT TextTag FROM InputField WHERE LocationId=?keep)`; then `UPDATE InputField SET LocationId=?keep WHERE LocationId=?old`.
   6. `TagMap.LocationId` — **dedup** on `UNIQUE (TagId, LocationId)`: `DELETE FROM TagMap WHERE LocationId=?old AND TagId IN (SELECT TagId FROM TagMap WHERE LocationId=?keep)`; then `UPDATE TagMap SET LocationId=?keep WHERE LocationId=?old`.
   7. `PlaylistItemLocationMap.LocationId` — **dedup** on `PRIMARY KEY (PlaylistItemId, LocationId)`: `DELETE FROM PlaylistItemLocationMap WHERE LocationId=?old AND PlaylistItemId IN (SELECT PlaylistItemId FROM PlaylistItemLocationMap WHERE LocationId=?keep)`; then `UPDATE PlaylistItemLocationMap SET LocationId=?keep WHERE LocationId=?old`.
   Comment each dedup: deliberate, tested divergence from Python's blind UPDATE (which would raise on a shared secondary key); avoids both the constraint violation and a dangling reference.

d. **Un-downgradeable preflight (HIGH-1) — BEFORE the DDL rebuild, AFTER the merge.** The merge only de-duplicates null-Book/Chapter rows under U2. U1 and U2 both cover ALL Location rows, and U2 was absent in v16, so an archive may still hold a residual collision the merge cannot fix (e.g. two non-null-BookNumber rows sharing the six U2 columns, or two rows sharing U1). Run an explicit preflight over ALL remaining Location rows for BOTH uniques:
   `SELECT COUNT(*) FROM (SELECT 1 FROM Location GROUP BY BookNumber,ChapterNumber,KeySymbol,MepsLanguage,Type HAVING COUNT(*)>1)` and the analogous GROUP BY over `(KeySymbol,IssueTagNumber,MepsLanguage,DocumentId,Track,Type)`. NOTE SQLite NULL-grouping semantics: `GROUP BY` treats NULLs as equal (matching the UNIQUE index's collation of NULL — verify: SQLite UNIQUE treats NULLs as DISTINCT, but GROUP BY treats them as equal, so a raw GROUP BY over-reports. To match the actual constraint, only count a group as a violation when the constrained columns are such that the UNIQUE would fire — i.e. exclude groups where any indexed column is NULL if SQLite's UNIQUE lets NULLs coexist). Simplest robust approach: instead of GROUP-BY math, attempt the rebuild and catch the UNIQUE error, but STILL surface it as a NAMED typed error — wrap the `INSERT INTO Location_new SELECT` and, on a UNIQUE constraint failure, return `SchemaDowngradeFailed { reason: "archive cannot be downgraded to v14: two Locations violate a v14 uniqueness constraint that v16 does not enforce" }`. Prefer the explicit preflight for a clearer message; if implementing the GROUP-BY preflight, MUST get the NULL semantics right (test with a NULL-column non-collision to prove no false positive). Either way: the transaction rolls back on this error, so the DB stays v16 and nothing is written.

e. **DDL rebuild** (AFTER merge + preflight): `execute_batch(CREATE_LOCATION_V14)`; `INSERT INTO Location_new SELECT <10 cols> FROM Location` (static column list; downgrade always drops Specialty/Edition) — map a UNIQUE failure here to the HIGH-1 named error; `DROP TABLE Location; ALTER TABLE Location_new RENAME TO Location;`; `tx.pragma_update(None, "user_version", 14_i64)`. Do NOT recreate IX_Location_Media or other Location indexes (Python omits them).
