  <action>
Implement `pub fn downgrade_to_v14(conn: &mut Connection) -> Result<(), ArchiveError>` mirroring `upgrade_to_v16`'s structure (upgrade.rs:205-242):

1. Read `PRAGMA user_version`. `==14` → `Ok(())` (idempotent, D4-06 supports re-entry). If not 16 → `Err(SchemaDowngradeFailed { reason: "expected user_version 16, found {v}" })`.
2. `conn.execute_batch("PRAGMA foreign_keys = OFF;")` on the connection BEFORE opening the tx (pragma is a no-op inside an active tx — upgrade.rs:229 finding 6; this build does NOT default FK off). Wrap the whole thing in a `PragmaGuard` so FK/journal/etc. restore on return (the guard borrows `&conn`; use `conn.unchecked_transaction()` like delete.rs:224 since the guard holds a shared borrow). Set FK off AFTER constructing the guard.
3. Open transaction. Call `run_downgrade_ddl(&tx)`. On Ok, `tx.commit()`; any Err rolls back on drop. Map every rusqlite error through `map_sqlite_err`.

Implement `fn run_downgrade_ddl(tx: &Transaction) -> Result<(), ArchiveError>`:

a. **Grouping:** run the grouping query WITH `ORDER BY LocationId` (see interfaces). Build a `BTreeMap<String, Vec<i64>>` (or IndexMap) keyed by the composite `KeySymbol|IssueTagNumber|MepsLanguage|DocumentId|Track|Type`. CRITICAL NULL rendering (research pitfall): render each key component so two NULLs collide identically to Python's `None` — use a canonical token for NULL (e.g. format `Option<i64>`/`Option<String>` where `None` → the literal string `"None"` to match Python's f-string, OR any consistent sentinel; document the choice). Because rows arrive ascending by LocationId, `ids[0]` per group is the LOWEST — the survivor. Keep insertion order within each group's Vec.

b. **Remap:** for each group with `len>1`, `keep_id = ids[0]`; for each `old_id` in `ids[1..]`, run the 7 UPDATEs in verbatim order (interfaces), all parameterized binding `(keep_id, old_id)`, then `DELETE FROM Location WHERE LocationId = ?old_id`.

c. **TagMap shared-tag collision (A1 CONFIRMED, documented divergence from Python):** the blind `UPDATE TagMap` would trip `UNIQUE (TagId, LocationId)` when both merged Locations share a TagId. BEFORE the TagMap UPDATE, dedup: `DELETE FROM TagMap WHERE LocationId = ?old_id AND TagId IN (SELECT TagId FROM TagMap WHERE LocationId = ?keep_id)` — drops the merged-away Location's duplicate tag mappings so the survivor keeps its single (TagId, keep_id) row — THEN run the plain `UPDATE TagMap SET LocationId = ?keep WHERE LocationId = ?old`. Document in a comment: this dedup-then-repoint is a deliberate, tested divergence from Python's blind UPDATE (which would raise on shared tags); it avoids both the UNIQUE violation and a dangling TagMap row. Do NOT use bare `UPDATE OR IGNORE` alone — it would leave an orphaned TagMap row pointing at the deleted old_id.

d. **DDL rebuild** (AFTER the remap so the new second-UNIQUE is satisfied by de-duplicated data): `execute_batch(CREATE_LOCATION_V14)`; `INSERT INTO Location_new SELECT <10 cols> FROM Location` (static column list, no conditional logic — downgrade always drops Specialty/Edition); `DROP TABLE Location; ALTER TABLE Location_new RENAME TO Location;`; `tx.pragma_update(None, "user_version", 14_i64)`. Do NOT recreate IX_Location_Media or the other Location indexes (Python omits them; research §DDL delta).
  </action>
