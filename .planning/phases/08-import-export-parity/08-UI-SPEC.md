# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope guard:** This phase's UI surface is exactly: (1) per-category `.txt` export (5 categories: Annotations, Bookmarks, Favorites, Highlights, Notes), (2) per-category `.txt` import with a NEW added/updated/skipped(/deleted for Notes' bucket-delete case) preview shape (D8-09), (3) Playlist `.jwlplaylist` export/import, (4) Playlist media add (file picker, SHA-256 dedup, on-disk copy + thumbnail, partial-completion reporting), (5) Playlist item delete's media reference-counting (shared-media-survives messaging). App icons/logo/About/version display/auto-update/localization/theme/window-geometry are **out of scope** (ROADMAP Phase 11) and are **not** specified here — the checker must not flag their absence as a gap. Incremental/changed-only export (Phase 9) and N-way merge (Phase 10) are also out of scope. `.xlsx`/`.md` formats are explicitly deferred per D8-01 and are not specified.

Exceptions carried forward and extended this phase:

- **44px row height** reused for every new bounded list this phase adds: the media-add file-result list (added/skipped/failed rows) and the playlist media-delete reference-count summary rows. Both lists are bounded by a single file-picker selection (tens of files, not thousands) — **not virtualized**, same rationale Phase 7 used for its tag/edition lists. DATA-01's virtualization mandate stays scoped to archive browse data.
- **Progress affordance for media add: a determinate text counter, not a progress bar.** `"Copying files… 3 of 12"` (Body 14/400, muted) replaces the row list while the `add_images`-equivalent apply runs. No new `<progress>`/bar component is introduced — this project has never shipped a progress bar (Phase 5's Merge uses the same busy-button + disabled-controls pattern for its C-callback-driven native operation), and a plain counter is legible at the file counts this operation handles (tens of files) without inventing new chrome. If the planner's backend can stream per-file progress events, this counter can update live; if not, it may jump straight from "Copying files… 0 of 12" to the completed result list — either is acceptable, this is a copy/layout contract, not an events-API mandate.
- **No new radii, no new shadows.** Import preview and media-add/delete dialogs are `EditPreviewDialog` instances (12px radius, no shadow, dimmed backdrop) — this phase adds zero new dialog chrome. The one new non-modal surface (none — see Component Inventory, no new popovers this phase) does not arise, so Phase 7's "first `box-shadow`" (`.color-menu`/`.utilities-menu`) is not extended further here.
- **File-result list row (added/updated/skipped/failed):** 44px row, a leading **status glyph is a literal Unicode/ASCII character, not an icon** (`✓` added/updated, `–` skipped, `✕` failed — matches `JwlCoreNotice`'s `×` and Phase 7's `▾` precedent of zero-icon-dependency), followed by the filename/label, Body 14/400. Status glyph uses `--text-muted` for skipped, `--brand-primary`-adjacent existing "added" convention is not defined elsewhere so **reuses `--text-primary`** for success (no new green/success token exists in this app — see Color below), `--destructive` for failed.

**Accent reserved for** (extends Phase 1/7's list — every addition is an instance of an already-reserved role, not a new one):
- Focus ring on the file-result list rows and any new button (same `outline: 2px solid var(--brand-primary)` convention).
- No new "active/selected" surface is introduced this phase (file-result rows are a read-only summary, not a selectable list).

**No new "success green" token — this app has none, and this phase does not add one.** The added/updated file-result rows use `--text-primary` (not a new emerald/green), matching the deliberate absence of a semantic-success color anywhere in the shipped app (Phase 1-7 never needed one; `EditPreviewDialog`'s "added" counts render in the same plain `--text-primary` as everything else). Global `design-preferences.md`'s emerald-for-good status convention is a web-dashboard pattern this desktop app has never adopted and does not adopt here — introducing color-coded status (green/amber/red pills) for a three-state added/skipped/failed list would be new visual vocabulary the app doesn't otherwise use; the ASCII glyph (`✓`/`–`/`✕`) already carries the distinction without color, so failure alone earns `--destructive` (an existing reserved role) and everything else stays `--text-primary`/`--text-muted`.

**Destructive — no new exception this phase.** Neither import nor media-add/delete rises to Mask's "most irreversible operation" tier (D8-09 confirms import previews as an added/updated/skipped diff, not a wipe; media delete only removes files no longer referenced, with the DB row as the authoritative source per D8-07). All of this phase's confirm surfaces stay at the **standard** `EditPreviewDialog` restraint level (destructive red confined to a Confirm button, when a delete is involved at all) — matching Phase 7's own "these don't need Mask's escalation" reasoning for its non-Mask ops.

### Dialog-by-dialog confirm copy

**Export (5 txt categories + Playlists) — no preview dialog at all (D8-09):** Export never mutates the archive, so it skips the dry-run/`EditPreviewDialog` chain entirely. Flow: click "Export…" → native save-file dialog (Tauri `dialog` plugin, suggested filename `{category}.txt` / `{category}.jwlplaylist`) → on confirm, the command runs synchronously (file I/O only, no DB write) → a **transient inline confirmation replaces the button label** for ~2s: *"Exported"* (reuses the existing busy-label convention shape — `"{Verb}ing…"` while pending, here a short post-success flash instead of a toast, since this app has never shipped a toast system and Export's success has no further consequence to track). On failure: standard `ErrorBanner` with `export_failed` copy (below) — the archive is unaffected either way, so there is nothing to roll back or represent as "unchanged."

**Import (5 txt categories) → NEW preview shape, `EditPreviewDialog` with an added/updated/skipped framing (D8-09):**
- Flow: click "Import…" → native open-file dialog → dry-run parses the file and returns the would-be result → `EditPreviewDialog` opens automatically (no separate parameter-picking step — the file selection *is* the only parameter, unlike Tag/Favorite's pick-then-preview two-step).
- Title: **"Import {Category}?"** (e.g. "Import Notes?").
- Summary is the **one deliberate new prop this phase adds to `EditPreviewDialog`** — see Component Inventory `previewMode="import"`. Renders three clauses, each present only when its count is nonzero, joined with line breaks (mirroring Mask's multi-line `<br/><br/>` summary precedent from Phase 7):
  - *"{N} new record{s} will be added."* (from `report.added`, using the standard total-across-tables sum already computed for Delete/Sort-Tags summaries)
  - *"{N} existing record{s} will be updated."* (from `report.overwritten` — this is the ON CONFLICT DO UPDATE path, e.g. Annotations import's upsert)
  - *"{N} record{s} in this file will be skipped (already present)."* (a NEW `DryRunReport` field the backend must expose — see UI Considerations "unresolved" row below; distinct from "updated," a skip is an exact-duplicate the import silently no-ops on, e.g. Favorites' string-level dup check D8-specifics)
  - Zero-everything case: *"Nothing in this file is new — every record already matches what's in this archive."*
  - **Notes-only extra clause**, only when the file targets a title-character bucket the import will bulk-delete first (`:1946-1955`, D8-09's own callout): *"Importing will first delete the {N} existing Note{s} under \"{bucket}\" before adding the file's records."* — rendered as a genuine `deleted` count from `report.deleted`, styled identically to the existing Delete-preview's deleted-count line (no new visual treatment; D8-09 explicitly requires this NOT be silent).
- Confirm: **"Import {Category}"**, pending: **"Importing…"**
- **Fail-fast is a pre-dialog state, not a dialog state (D8-04):** a malformed file never reaches the preview — the dry-run itself returns `Err(ImportError{category, line, reason})`, surfaced via the standard `ErrorBanner` *before* `EditPreviewDialog` ever opens. Copy: *"Couldn't read this file — line {line}: {reason}. Choose a different file, or check that it was exported from JW Library or JWL Manager."* This keeps the safety framing honest: the user never sees a preview promising a partial result the app wouldn't actually commit.

**Import (Playlists, `.jwlplaylist`) → same `EditPreviewDialog` shape, one extra clause:** Title: **"Import Playlist?"**. Summary adds a leading clause naming the playlist: *"This adds the playlist \"{Name}\" and its {N} media file{s}."* followed by the same added/updated/skipped lines as the txt categories (playlist import can also collide with existing `IndependentMedia` by hash — same dedup logic as media add, D8-06). Confirm: **"Import Playlist"**, pending: **"Importing…"**.

**Add Media → its own file-result flow, NOT a pick-then-`EditPreviewDialog` two-step (deliberate deviation, justified below):**
- Rationale for deviating from the Tag/Favorite two-step: media add has no meaningful "preview" beyond the dry-run's row/table counts — the real information the user needs is *which specific files* landed, were deduped, or failed, which is a **per-file result list**, not a `DryRunReport` table-count summary. Reusing `EditPreviewDialog` verbatim here would either lose per-file granularity or need a second, incompatible summary shape bolted onto the same component. Per the safety framing ("legible partial-failure reporting, not an all-or-nothing lie"), this phase adds a **new component**, `MediaAddDialog`, that still opens via the file-picker → dry-run(-of-sorts, see below) → confirm chain, but replaces `EditPreviewDialog`'s summary body with the file-result list.
- Because media add's real side effects are file-copy + thumbnail generation (not row-count-predictable in advance the way SQL is), its "preview" step is a **cheap pre-check only** — SHA-256 hash each selected file and classify it up front as **new** / **duplicate-of-existing** (by hash) / **unreadable** (bad magic bytes) — before any copy happens. This pre-check list IS the confirm surface (no separate blank "preview" screen then a second "result" screen): rows show their pre-check classification, Confirm commits only the "new" rows, and after Confirm the SAME rows update in place from "new" to "added"/"failed" as each file is actually processed (D8-06's copy+thumbnail step can still fail per-file even after a successful hash pre-check — disk full, permission denied — so the row's final state is always the true outcome, never assumed from the pre-check alone).
- Dialog title: **"Add media?"** Pre-check row copy: `"{filename}"` + trailing Label-styled classification — *"new"* (`--text-muted`), *"already added"* (`--text-muted`, skip — matches SHA-256 dedup being a legitimate no-op, not a failure), *"unreadable — not a supported image"* (`--destructive`-tinted text, no glyph color per the "no new success-color" rule above, this one DOES use `--destructive` since unreadable is a real per-file failure, not a benign dedup skip).
- Zero-new-files case (every selected file already a duplicate): Confirm button disabled, inline note replaces the list: *"All selected files are already in this archive."*
- Confirm: **"Add Media ({N})"** where N = count of "new" rows (updates live if the user reopens the picker to add more before confirming — out of scope to spec further, single-pick-then-confirm is sufficient for Phase 8). Pending: rows transition to **"Copying files… {i} of {N}"** counter (see Spacing) replacing the static list header.
- Post-completion state (dialog stays open, does not auto-close): each row shows its final glyph (`✓ added`, `✕ failed: {reason}`), plus a top summary line: *"{added} added, {failed} failed."* (omit the failed clause when 0). A single **"Done"** button closes the dialog and refreshes the Playlists media list — replacing the two-button Confirm/Cancel footer once processing completes, since Cancel/Confirm no longer apply to a completed run.
- Cancel (pre-confirm only): standard, discards the picked file selection, no backend call.

**Delete (Playlists) → `EditPreviewDialog`, standard, with a NEW shared-media clause:**
- Title: **"Delete {N} playlist item{s}?"** (reuses the exact "Delete (N)" pattern already shipped for every other category).
- Summary — extends the default deleted-count rendering with one added clause distinguishing orphaned vs. shared media, per D8-07/the safety framing's "shared media survives" requirement: *"This deletes {N} playlist item{s}. {M} media file{s} used only by these items will also be removed. {K} media file{s} will be kept because {they're/it's} still used by other playlist items."* — all three counts come straight from the `DryRunReport`'s table-scoped deltas (`deleted.IndependentMedia` for the removed count; a difference against the pre-selection reference count for the kept count — exact DTO shape is Claude's Discretion for the planner, see Component Inventory). Zero-shared case (no media survives): drop the third sentence entirely rather than saying "0 files will be kept."
- Confirm: **"Delete"**, pending: **"Deleting…"** (unchanged from every existing Delete instance).

### New error codes (extends `app/src/lib/errors.ts`)

Per Phase 7's D7-13 precedent (per-op-code sentences, keyed off `err.code`), these follow the same shape as the existing table:

| Code | Copy |
|------|------|
| `export_failed` | "Couldn't export this file — the archive is unchanged. Check that the destination folder is writable, then try again." |
| `import_malformed` | "Couldn't read this file — line {line}: {reason}. Choose a different file, or check that it was exported from JW Library or JWL Manager." (`{line}`/`{reason}` interpolated from the `ImportError` payload, per D8-04's typed-error shape) |
| `import_failed` | "Couldn't import this file — the archive is unchanged. Try again, or close and reopen the archive if the problem continues." |
| `media_add_failed` | "Couldn't add media — no files were added and the archive is unchanged. Try again, or choose different files." (this is the whole-operation failure path, e.g. the DB transaction itself failing — distinct from a per-file "unreadable"/copy failure, which renders inline in the `MediaAddDialog` row list, never as a full-dialog error) |
| `media_delete_failed` | "Couldn't delete the selected playlist items — the archive is unchanged. Try again, or close and reopen the archive if the problem continues." |
| `zip_slip_rejected` (Playlist import) | Reuses the EXACT existing sentence from 01-UI-SPEC/`errors.ts` verbatim — no new copy, since D8-02 reuses the existing primitive and the existing rejection message already reads correctly for any zip container, not just the main archive. |
