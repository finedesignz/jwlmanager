<task type="checkpoint:decision" gate="blocking">
  <decision>Authorize irreversible on-disk deletion of playlist media files by the apply path of playlist item delete.</decision>
  <context>
    Every mutation shipped in Phases 1-7 was reversible by discarding the working copy — nothing left the SQLite transaction boundary. Task 4 introduces the project's first `std::fs::remove_file` against user media inside the archive working directory. SQLite's rollback does not undo it, so this is rated **one-way** under the phase's reversibility gate and is the only decision in Phase 8 that earns a blocking gate.

    The design being authorized (D8-07, PD-3): reference-count each media file against the REMAINING playlist items — never the deleted selection — separately for thumbnails and for full media; commit the DB deletion FIRST; then best-effort remove only the files no surviving item references, silently ignoring a missing file exactly as the Python does. `dry_run_delete_playlist_items` is structurally incapable of reaching the removal code — it calls only the DB half of a shared helper.

    The alternative considered and not chosen: leave every media file on disk forever and delete only the `IndependentMedia` rows. That is fully reversible but diverges from Python parity and grows the archive without bound on every playlist edit, which the trim/save pipeline would not reclaim.
  </context>
  <options>
    <option id="approve-parity">
      <name>Approve the Python-parity design as specified</name>
      <pros>Full parity with the Python app; archives do not accumulate orphaned media; the removal is provably unreachable from any preview path and provably scoped to files no surviving item references</pros>
      <cons>An irreversible filesystem deletion enters the codebase for the first time; a reference-counting bug would destroy user media that SQLite rollback cannot restore</cons>
    </option>
    <option id="rows-only">
      <name>Delete `IndependentMedia` rows only; never touch the filesystem this phase</name>
      <pros>Nothing irreversible ships; strictly safer</pros>
      <cons>Diverges from Python parity; orphaned media files accumulate in every archive and are never reclaimed; defers the same decision to a later phase with no new information available then</cons>
    </option>
  </options>
