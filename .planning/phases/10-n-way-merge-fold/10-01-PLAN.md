<objective>
Prove the N-way fold end-to-end on 3 archives, through every layer it will ever
touch: a generalized copy-source staging primitive, one shared fold chain, the
aggregate dry-run, the single atomic promote, two Tauri commands, and the two
tests that are this phase's whole reason for existing — all-sources-carried and
fold == chained-pairwise in the same order.

Purpose: the fold is not a new algorithm, it is N-1 correctly-sequenced calls to
Phase 5's already-hardened primitive. The risk is entirely in the sequencing and
in the cleanup discipline, so the sequencing gets proven first, on the smallest N
that can actually expose it (N=3 — N=2 is just Phase 5 again).

Output: `fold_merge_dry_run` / `fold_merge_commit` commands backed by a tested
chain, ready for the failure envelope (plan 02) and the UI (plan 03).
</objective>

<design_resolutions>
Settled during planning; do not re-derive or re-litigate.

**Order is user-visible and load-bearing (D10-01).** `jwlCore.mergeDatabase` does
in-place content UPDATEs at matched PKs (`archive/merge.rs:17-24` module docs), so
the later step in a fold wins a contested identity key. `fold(A,B,C)` and
`fold(A,C,B)` genuinely diverge — exactly as hand-chaining Phase 5 merges already
does. The fold is SEQUENTIAL and ORDERED; order is the caller's list order; the
round-trip test compares fold against chained-pairwise IN THE SAME ORDER and must
never assert commutativity.

**Schema heterogeneity — DECIDED, not deferred to the executor.** Phase 5 D5-08
already settled the pairwise case: the DESTINATION is normalized to v16 at open
time by Phase 1/3's existing open-path upgrade, each SOURCE is handed to jwlCore
as-is, and `downgrade` is always `false`. Phase 10 inherits that verbatim and adds
nothing: sources at v12-v16 are passed through untouched, no per-source
pre-upgrade pass is introduced, no source archive is ever rewritten (that would
violate the read-only-inputs prohibition), and a source jwlCore refuses is a
normal step-k `MergeFailed` handled by plan 02's failure envelope. Explicit
downgrade-during-fold remains deferred with Phase 5's D5-08.

**Blocking / progress — DECIDED (D10-07).** The native call is synchronous and
N-1 of them run back-to-back. Tauri commands already execute off the WebView UI
thread, so the window stays responsive; `setProgressCallback` stays unwired
(process-global callback state, extra unsafe surface, cosmetic gain — Phase 5
D5-05's rejection, unchanged and not reopened). Tradeoff accepted and disclosed:
a large N-archive fold shows a single busy state for its whole duration with no
percentage and no per-step feedback. The command therefore must not hold the
state mutex any longer than the shipped `merge_commit` does.

**Minimum N = 3 at the command boundary.** 1-2 archives already have the shipped
open and `merge_dry_run`/`merge_commit` flows; a fold call with fewer than 3
sources is a caller bug and is rejected with `MergeFailed { reason }`, not
silently degraded.

**Failing-step identification (RESEARCH Open Question 2 — resolved).** Fold the
1-indexed source position into the existing `MergeFailed { reason }` string
(`format!("source {i} of {n}: {inner}")`). No new enum variant, no DTO shape
change; `reason` is already never leaked over IPC.
</design_resolutions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user filesystem -> backend | N user-chosen `.jwlibrary` files, each an untrusted zip, extracted once per fold step |
| backend staging -> live session DB | the single atomic promote at the end of the fold is the only write to `session.db_path` |
| backend -> native jwlCore FFI | N-1 sequential `mergeDatabase` calls with directory paths marshalled as C strings |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-01 | Tampering | extraction of each of the N source archives | high | mitigate | Every source goes through `extract_zip_slip_safe` into its own `step_i/merge` directory; no raw `ZipArchive` loop is written anywhere in this phase |
| T-10-02 | Tampering | partial-merge exposure across N-1 failure windows | high | mitigate | No fold step writes to `session.db_path`; one `atomic_replace` after the final step only; `session.dirty` set only after that returns Ok (plan 02 proves the pristine-on-failure property) |
| T-10-03 | Tampering | source archives mutated by the fold | high | mitigate | Sources are opened read-only for extraction and never written; asserted by byte-comparison of all three inputs in `fold_merge_carries_all_sources` |
| T-10-04 | Denial of service | disk exhaustion from N-1 staged full-DB copies plus N extractions | medium | accept | Hobby-scale archives with single-digit N; the whole fold root is removed on every exit path, success or failure, so the footprint is transient and bounded by one fold |
| T-10-05 | Tampering | interior-NUL / crafted path into the FFI boundary | low | mitigate | `dir_cstring`'s existing interior-NUL guard degrades to a typed `MergeFailed`, never UB; unchanged and applied identically per step |
| T-10-06 | Information disclosure | jwlCore `getLastResult()` detail reaching the UI | low | mitigate | The step index and inner reason go into `MergeFailed { reason }`, which the shipped `to_dto` mapping already never leaks over IPC (D-14) |
| T-10-SC | Tampering | cargo dependency supply chain | low | accept | Zero new dependencies; RESEARCH's Package Legitimacy Audit is N/A because `Cargo.toml` is untouched. A dependency that seems unavoidable is a BLOCKING checkpoint, not an executor decision — the live crates.io legitimacy check is unavailable in this environment |
</threat_model>
