<objective>
Give the fold a surface: pick many archives at once, see and control their order,
approve one cumulative preview, watch one busy state, and land back on a refreshed
grid.

Purpose: order is the user-visible semantic of this phase. A UI that hides or
normalizes it would make the backend's honest order-sensitivity look like
nondeterminism to the user.

Output: a "Merge Multiple Archives…" command-bar action backed by a reorderable
source list and the shipped preview dialog.
</objective>

<ui_decisions>
No UI-SPEC exists for this phase, so the surface is specified here against the
shipped conventions.

- Entry point: a new `CommandBar` action labelled "Merge Multiple Archives…",
  sitting next to the existing "Merge Archive…" and following the same
  ellipsis-means-picker convention and the same `runAction` busy/aria-busy
  pattern (`CommandBar.tsx:231-283, :350-360`).
- Picker: the same `open()` + `FILTERS` call the merge action already uses, with
  `multiple: true`. A cancelled picker aborts the whole action via `onCancelled`,
  exactly as the shipped merge does.
- Source list: a new `FoldMergeDialog`, styled to the shipped dialog conventions
  (`EditPreviewDialog`), listing the chosen files by base name in order with a
  1-based position number, Move-up / Move-down controls per row, and a Remove
  control. It states in one sentence that the archives are merged in the order
  shown, top to bottom, and that when two archives change the same record the
  later one wins. Its Continue action is unavailable below 3 entries, with the
  reason shown rather than a silently-dead control.
- Preview: the shipped `EditPreviewDialog` with the aggregate `DryRunReport`,
  summary copy naming the number of source archives and stating the counts are
  the combined effect of all of them in the shown order.
- Busy: one `aria-busy` state for the whole fold; no percentage, no per-step text
  (D10-07).
- Read `~/.claude/design-preferences.md` before writing markup.
</ui_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user -> frontend | file choices and their order, taken from the native picker and local reordering |
| frontend -> Tauri command boundary | the ordered `sourcePaths` array; all validation of count and content is re-done in Rust, never trusted from here |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-12 | Tampering | frontend reordering the array between preview and commit | high | mitigate | The commit sends the same array the preview was computed from; asserted by test comparing both invoke payloads |
| T-10-13 | Spoofing (of trust) | user believes order does not matter | medium | mitigate | The dialog states the order rule in plain language; no string may imply commutativity |
| T-10-14 | Elevation of privilege | frontend-side count check treated as the real guard | medium | mitigate | The disabled Continue below 3 entries is UX only; the Rust command independently rejects fewer than 3 with a typed error (plan 01) |
| T-10-15 | Denial of service | double-invoking a long fold | low | mitigate | `runAction`'s existing pending/aria-busy guard blocks re-invocation, as it already does for the two-archive merge |
| T-10-SC | Tampering | npm dependency supply chain | low | accept | Zero new frontend dependencies; reordering is local array manipulation, no drag-and-drop library |
</threat_model>
