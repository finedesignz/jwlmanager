<objective>
Expand the proven Notes slice to the three flat pipe-delimited categories: Favorites,
Bookmarks and Highlights. Each gets an id-carrying read path, a per-category identity
key, and an `export_<category>_incremental` command reusing `diff_records` from 09-01.

Purpose: these three are structurally the simplest — one record is one line, and the
line IS the hash input verbatim — so the whole plan is mechanical application of the
09-01 design. The one real subtlety is Highlights, whose identity key must exclude the
mutable colour so a recolour reports as modified rather than as an add plus a delete.

Output: three more live incremental-export commands with their behaviour tests.
</objective>

<identity_key_specification>
Both sides hash the FULL wire line verbatim — the whole hash input is the line as
written or as read, with no field selection and no normalization. Only the identity key,
used solely for summary labelling, is field-scoped. Field indices below are zero-based
into the pipe-split line, in the exact order each category's shipped SQL selects.

**Favorites** (6 fields: DocumentId, Track, IssueTagNumber, KeySymbol, MepsLanguage,
Type — `export.rs:72-74`). Every field is identity; there is no mutable content field on
the wire. Key is the whole line. Consequence: a Favorite can only be added or removed,
never modified, and the summary's modified count is structurally always zero. Document
this in the code and assert it, rather than leaving a reader to wonder whether it is a
bug.

**Bookmarks** (12 fields — `export.rs:162-165`). Key is fields 0 through 7 inclusive
(BookNumber, ChapterNumber, DocumentId, IssueTagNumber, KeySymbol, MepsLanguage, Type,
Slot). Slot is what distinguishes two bookmarks at one location. Mutable, therefore
excluded from the key and detected via the line hash: Title, Snippet, BlockType,
BlockIdentifier.

**Highlights** (13 fields — `export.rs:363-366`). Key is fields 0 through 3 (BlockType,
Identifier, StartToken, EndToken) plus fields 6 through 12 (the seven Location fields).
Excluded from the key, therefore surfacing as modified: ColorIndex (field 4) and Version
(field 5). A token-span edit changes the key and so reports as an add plus a deleted
candidate rather than a modification — correct for the exported file either way, and
noted in the code as intentional.

Identity keys are `String`s built by joining the selected fields with the same unit
separator `record_hash` uses, so `diff_records` instantiates at `K = String` for all
three.
</identity_key_specification>

    `highlights_identity`, each taking a wire line and returning the identity key string
    per the specification above, splitting on the pipe character and joining the selected
    indices with the unit separator. A line with an unexpected field count must yield a
    key derived from the whole line rather than panicking or indexing out of bounds — an
    over-conservative key is the safe direction. Add
    `split_prior_lines(text: &str) -> Vec<String>` returning the data lines of a
    CRLF-normalized flat-format prior file, applying the same "a line containing a pipe
    is a data line" filter the shipped parsers use so the header never enters the diff.

    Unit-test in `diff.rs`: the Highlights key is invariant under a ColorIndex change and
    varies under an Identifier change; the Bookmarks key is invariant under a Title change
    and varies under a Slot change; the Favorites key varies under any field change; a
    short line does not panic.
