<objective>
Prove incremental export end-to-end on Notes — the hardest and the criterion-named
category — through every layer: a new `db/io/diff.rs`, a record-text hashing scheme,
a `read`-side identity refactor in `export.rs`, one `export_notes_incremental` Tauri
command, the `CategoryList` file-picker + summary UI, and a convergence test.

Purpose: Notes is the only category with timestamps on the record (`{CREATED=}`,
`{MODIFIED=}`), the only one with an export-time auto-fill transform (HEADING), and
the only one with a wall-clock `now` fallback. If the diff is right for Notes it is
right for the four simpler categories, which plans 02-03 then expand into.

Output: a working "Export changed notes since a prior export" flow plus the shared
diff machinery every later plan reuses.
</objective>

<design_resolutions>
The three research assumptions A1-A3 and Open Question 1 were resolved by direct source
reads during planning. Record the findings; do not re-derive them.

**A1 — RESOLVED, confirmed true.** `AnnotationRecord.label: String` (`import.rs:792-801`)
is the raw `TextTag` string lifted straight from the `{LABEL=}` bracket, and
`export.rs:331` writes `{LABEL=}` from `AnnotationExportRow.label`, itself
`SELECT TextTag` (`export.rs:258`). `AnnotationRecord.doc: Option<i64>` comes from
`{DOC=}`. Annotations identity is therefore recoverable from a prior file — used in
plan 09-03.

**A2 / Open Question 1 — RESOLVED, and made moot.** `NoteRecord` (`import.rs:1423-1450`)
carries `created, modified, tags, color, range, lang, pub_sym, bk, ch, vs, issue, doc,
block, heading, title, note`. `heading` is necessarily the POST-autofill wire value.

**A3 — RESOLVED, and it invalidates the field-by-field approach.** `parse_highlights_file`
applies a BLANKET `None` -> empty-string replacement across the whole line before
splitting (`import.rs:1089`+, documented at `:1050-1052`). That transform is lossy and
NOT reversible, so a wire line cannot be faithfully reconstructed from a parsed
`HighlightRecord`. Any design that hashes parsed struct fields on the prior side and SQL
values on the live side must keep two normalization pipelines byte-identical forever —
exactly the drift the research flagged as the phase's core risk.

**Consequent decision (refines D9-03, supersedes RESEARCH Pattern 1's field-list audit):
hash the WIRE RECORD TEXT on both sides.**
- Live side: the exact bytes `export_<category>` would write for that record.
- Prior side: the exact record text as read out of the prior file after CRLF
  normalization.
Both sides are then the same grammar produced by the same authority, so the
normalization-divergence class of bug (RESEARCH Pitfall 1, A2, A3) cannot occur by
construction. No per-field common-subset audit is needed or performed.

**Timestamp exclusion.** Notes is the only category whose wire record embeds timestamps.
Its hash input is the record text with the leading `{CREATED=...}{MODIFIED=...}` bracket
pair removed, applied identically on both sides. This is what satisfies IO-04 criterion 2
textually rather than by field bookkeeping. No other category needs any exclusion; the
other four wire formats contain no timestamp at all.

**Identity keys (refines D9-02).** No wire format encodes its category's DB primary key —
not `NoteId`, not `BlockRangeId`, not `BookmarkId`, not `TagMapId`, not `LocationId`. D9-02
as literally written is therefore unimplementable on the prior side for EVERY category,
not just Annotations. Identity must be a wire-recoverable natural key. For Notes:
the `{CREATED=}` value. Created is stable for the life of a note and is on the wire;
it is used ONLY to label a record as "modified" rather than "added+deleted" in the
summary, and NEVER as a change-detection signal — so this does not weaken criterion 2.

**The invariant that makes identity errors harmless (state this in the module doc):**
the exported id set is defined purely as `{ live records whose hash is absent from the
prior hash set }`. It does not consult the identity key at all. The identity key only
partitions that set into "added" versus "modified" for the summary, and only names the
deleted candidates. Therefore every failure mode of the identity layer — a collision, a
churned `{CREATED=}`, a coincidence — biases toward exporting a record that did not need
exporting, never toward omitting one that did. Over-export is safe; under-export is the
data gap the phase exists to prevent.
</design_resolutions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user filesystem -> backend parser | The prior export .txt is user-supplied, possibly hand-edited or hostile, and is parsed before any use |
| backend -> user filesystem | The output .txt is written to a user-chosen path via the native save dialog |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Tampering | prior-file parse in `export_notes_incremental` | medium | mitigate | Run `parse_notes_file` as a fail-fast validation gate and propagate its typed `ImportMalformed` error with `?` before any output file is created; never degrade to an implicit full export |
| T-09-02 | Information disclosure | absurdly large or deeply pathological prior file | low | accept | The shipped Phase 8 parsers are linear forward scans with no recursion and no backtracking regex; a large file costs memory proportional to its size, the same cost the already-shipped import path accepts |
| T-09-03 | Tampering (of trust, not of data) | hash-input divergence between live and prior sides | high | mitigate | Both sides hash the same wire record grammar produced by the single shared `format_note_record`; the timestamp bracket pair is stripped identically on both sides; proven by `timestamp_only_change_excluded` and `incremental_export_converges` |
| T-09-04 | Repudiation | user believes a change was exported when it was not | high | mitigate | Exported set is hash-set membership only, never identity-keyed, so identity failures over-export; asserted by the added/modified/deleted test matrix |
| T-09-05 | Elevation of privilege | SQL injection through the id selection | low | mitigate | All new SQL keeps the existing `params_from_iter` parameterization; the diff itself issues no new SQL beyond the extended read |
| T-09-SC | Tampering | cargo dependency supply chain | low | accept | Zero new dependencies this phase; `sha2` is already declared and in use since D8-06, so no package-legitimacy checkpoint is triggered |
</threat_model>
