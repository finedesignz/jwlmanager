<annotations_identity_resolution>
RESEARCH assumption A1 was verified during planning and holds: `AnnotationRecord.label`
(`import.rs:792-801`) is the raw `TextTag` string taken from the `{LABEL=}` bracket, and
`export.rs:331` writes `{LABEL=}` from the value `SELECT TextTag` produced
(`export.rs:258`). `AnnotationRecord.doc: Option<i64>` comes from `{DOC=}`, which
`export.rs:297` writes as the `Location.DocumentId` rendered through the string `None`
when NULL.

The Annotations wire format never encodes `LocationId` at all. D9-02's stated identity
therefore cannot be recovered from a prior file. Identity is the wire-recoverable pair
`(DOC, LABEL)` — a refinement of D9-02 in the direction its own rationale points, since
for any archive at rest `(DocumentId, TextTag)` and `(LocationId, TextTag)` are in
one-to-one correspondence. Instantiate `diff_records` at `K = String` by joining the DOC
text and the LABEL text with the unit separator, exactly as the flat categories do.

**The over-selection consequence, which must be disclosed rather than hidden.** The
shipped `export_annotations` takes `NonEmptyLocationIds`, so selecting a changed
annotation selects every `InputField` row at that location — its unchanged siblings ride
along into the output file. This is over-export, which the phase's central invariant
declares safe, and it matches the precedent already shipped for annotation delete
(`CategoryList.tsx`'s DELETE_COMMANDS comment: annotation delete is by LocationId, an
intentional over-selection). Do not fork the exporter to avoid it — D9-06 forbids that.
Instead make the summary honest: report the diff's own added and modified counts AND the
count of records the exporter actually wrote, so a user seeing more records than
modifications has the explanation in front of them.
</annotations_identity_resolution>
